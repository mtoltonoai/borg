# Phased Implementation Specification

This document defines the seven-stage structure within the [implementation specification set](implementation.md#phased-delivery-and-coverage). The main specification defines v1 scope, shared-specification precedence, capitalized-keyword meanings, fixed coverage targets and the distinction between planning and runtime evidence. Standalone keyword clauses below are v1 delivery-process obligations. The binding declaration schema is in [Duvet Cap](implementation.md#duvet-cap-declaration-contract).

Structured milestone acceptance and gate expectations specify delivery and qualification criteria. Shared requirements quoted inside a gate keep their shared identity and applicability; such quotation does not create another v1 requirement.

## Delivery Stages

### Stage 1: Reviewed, Testable Interface Contracts

Stage 1 MUST establish reviewed, testable interface contracts.

### Stage 2: Real Store Atomicity And Restart Proof

Stage 2 MUST demonstrate atomicity in a real store.

Stage 2 MUST demonstrate recovery of committed state after process restart.

### Stage 3: Durable Event And Session Processing, Fencing And Retry

Stage 3 MUST establish durable event and session processing.

Stage 3 MUST establish ownership fencing for that processing.

Stage 3 MUST establish retry behavior for that processing.

### Stage 4: Direct Model And Tool Harness

Stage 4 MUST establish the direct model and tool harness.

### Stage 5: Remaining Capability Integrations

Stage 5 MUST integrate the remaining applicable capabilities.

### Stage 6: Integrated Fault, Recovery And Isolation Qualification And Real-Dependency Probes

Stage 6 MUST close integrated fault, recovery, and isolation qualification evidence.

Stage 6 MUST close applicable real-dependency probe evidence.

### Stage 7: Coverage And Conformance Closure

Stage 7 MUST close coverage and conformance obligations.

## Delivery And Evidence Throughout

Work within each stage MUST be divided into small, measurable milestones.

Tests and evidence MUST accumulate throughout implementation.

A stage boundary MUST NOT block independent work whose required decisions are approved and whose prerequisite interfaces and invariants are ready.

The stages are milestone views, not global barriers requiring unrelated work to
finish together. Contracts can be iterated for the next slice; stage 2 provides
early actual persistence and restart feedback, followed by durable event/session
integration. Stage 6 closes integration evidence rather than introducing the
first tests, fault scenarios or applicable probes. An in-memory simulation is
not proof of durability, and a small durable milestone is not completion of all
components or proof of the all-node durability guarantee.

References to capabilities use the stable IDs governed by the main specification and the linked [capability specification](implementation-capabilities.md). This stage structure selects no adapter, provider, runtime, engine, budget or exception.

## Phased Scale Qualification

Scale testing MUST exercise the intended production implementation and interfaces.

A scale qualification report MUST identify the hardware and workload profile it exercised.

Stage 6 scale qualification MUST demonstrate the simultaneous production scale target defined in the main specification.

Stage 7 closure MUST include the full-target scale evidence.

The [simultaneous production scale target](implementation.md#simultaneous-production-scale) is ten hosts, each concurrently operating at least one thousand agents and ten workspaces. Tests increase load on the same production architecture; they do not establish smaller substitute architectures as delivery milestones. Intermediate concurrency points are test parameters, not reduced acceptance targets. Workload, duration, latency/throughput expectations and failure-load capacity are explicit qualification inputs; none is invented by these scale gates.

| Stage | Scale qualification increment | Structured gate |
|---|---|---|
| 1 | Review the production architecture and resource accounting against the combined target; resolve the workspace delivery/interface allocation. | G_S1: SCALE_ARCHITECTURE and WORKSPACE_DELIVERY_ALLOCATION |
| 2 | Qualify real store/adapter atomicity and restart with target-derived concurrency and bounded connection, watch, snapshot and transaction resources. | DA_S2: SCALE_STORE_RESOURCES |
| 3 | Increase concurrently operating agents on the actual scheduler, session and event path; measure progress, bounded backlog and blocked-peer isolation. | S_S3: SCALE_AGENT_PROGRESS |
| 4 | Load the real owned model/tool loop with concurrent durable sessions; distinguish controlled model-service load from real provider capacity. | M_S4_FIRST: SCALE_MODEL_TOOL_LOOP |
| 5 | Integrate the actual multi-host placement, admission, workspace and capability paths; measure per-host resource use and backpressure. | SR_S5: SCALE_CAPABILITY_INTEGRATION |
| 6 | Exercise the complete ten-host, ten-thousand-agent, one-hundred-workspace workload simultaneously; add applicable fault, drain and restart scenarios. | G_S6: SCALE_COMBINED_QUALIFICATION |
| 7 | Require the exact-source full-target receipt and remaining coverage/conformance evidence. | G_S7: SCALE_EVIDENCE_CLOSURE |

Informative: the native workspace-service BUILD outcome is selected in the main specification. The WS capability declares the workspace delivery producers; their actual implementation and qualification remain required. The production host mapping and its structured producer/consumer interfaces must be resolved before combined scale qualification can pass. Collaboration tasks are not workspace execution environments. This specification records that missing work instead of treating an absent producer or synthetic handle as delivered. The workspace capacity requirement remains binding.

## Runtime Self-Delivery Qualification

The [runtime self-delivery requirement](implementation.md#runtime-self-delivery) is qualified through the intended production path. G_S1 defines workspace, repository, trusted validation and deployment-control-plane interfaces. SR_S5 integrates automatic source editing, submission, compilation, validation and artifact preparation. G_S6 demonstrates a working cluster carrying a runtime change through that path. G_S7 verifies the final human rollout decision against the exact artifact and target, after all mandatory machine checks.

These gates do not grant an agent approval authority. Tests performed in an agent's workspace remain development feedback; the protected checker produces its own release evidence. Intermediate preparation proceeds without per-change human approval, while the final rollout remains gated. The existing technology-approval rule for this implementation work is unchanged.
