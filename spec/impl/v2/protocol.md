# Task Runtime Interface

This is the concrete engineering interface for the first v2 application. The [main specification](implementation.md#task-and-worker-contract) owns the behavioral requirements. These private application records do not change a shared wire contract. Planning provenance binds this file's exact bytes; implementation and qualification are established by separate source-bound evidence.

## One Application And One Durable Owner

Build one Rust package with controller, worker and client modes. The controller opens local SQLite through one bounded blocking database queue; network/provider/repository operations do not hold database transactions open. Workers never open the database file. Avoid a separate framework or crate per state transition.

Use bounded typed JSON records for the private application API. Identities are opaque strings, revisions and generations are checked nonnegative integers, and durations/byte bounds are explicit configuration. Model-request accounting follows the initial policy below; observed token usage does not imply token-budget enforcement. Reject unknown operation kinds, invalid enum combinations, oversized bodies and conflicting identity reuse. Exact database table/index choices remain implementation-owned. Authentication comes from the configured host/SSH access boundary; identity fields describe the already authenticated actor and never authenticate themselves.

### Accepted Limit Metadata

Operational policy is selected from closed, versioned `RuntimeLimits` metadata. Startup accepts `--limits` for a selected file; omission loads the shipped `metadata/limits.json` seed data. Missing or unknown policy fields, invalid ranges and incompatible cross-field bounds refuse instead of acquiring consumer-local defaults or being silently clamped. Fixed encoding/library constraints and unknown external provider or Codex limits remain distinct from configurable policy. The HTTP parser receives the configured `transport.http_header_count`; its checked `constraints.http1_maximum_header_count` is the pinned dependency representation ceiling, not an operator-selected default.

`Definition.limit_overrides` can replace complete native, coding, collaboration or memory-notice groups. Admission resolves those groups against one global metadata revision and stores a server-owned `TaskInput.resolved_limits`: the exact global metadata, definition revision and effective execution values. A caller cannot supply an accepted snapshot. Definition identity/revision reuse with different settings refuses. Subsequent defaults do not reinterpret accepted inputs or original receipts; configured children resolve their own accepted settings through the same admission rules.

`collab_limits_get` exposes current global metadata separately from the calling task's accepted snapshot. It accepts no task selector or policy write. The explicit task deadline, model-request allowance, output/result byte bounds and delegation depth remain in `TaskInput.limits`, also available through `collab_task_get`. The browser displays those accepted task limits and retained metadata revisions, with current defaults labelled separately. Worker operational policy remains startup-owned, while task-bound execution and collaboration operations consume the accepted policy. The [limits guide](../../../../borg-runtime/docs/v2-limits.md) describes the retained-policy and format boundaries. This interface adds no provider quota, credential, kernel-control or protected-release authority.

### Initial Model Budget Defaults

New operator-facing task submissions default to 4294967295 model requests, the maximum value of the existing unsigned32-bit field. The browser no longer asks for a model-request budget. Legacy explicit form/API values and accepted task limits retain their exact meanings and replay identities. An omitted coding-child allowance in the browser's configured native workflow uses the largest compatible parent allocation after reserving its two native requests; an explicit child allowance is not rewritten. A maximum parent therefore permits a default child allowance of 4294967293. Invalid or overflowing explicit combinations still refuse.

Fine-grained cost/token budgets and hard enforcement of opaque Codex inner-request counts are deferred. Native requests continue to use acknowledged cumulative reservations; configured child-task allocations remain non-refundable reservations rather than measurements of hidden executor calls. Known usage stays observable, and unknown usage stays unknown. This change does not reset accepted limits or extend deadlines, output/result bounds, provider admission, host capacity, cancellation or recovery authority. It changes defaults and first-release qualification scope without changing task-wire, database or worker-state representations.

### Maximum Context Profile

The selected `gpt-6-astra` model has a documented 1050000-token context window. `constraints.provider_model_context_tokens` records that known external constraint. The optional `coding.model_context_window` is set to 1050000 in the current seed and is passed into the task-owned Codex startup configuration; no global Codex configuration is changed. Absent historical values retain the prior executor-default behavior and serialize without an added field. The browser labels such a prior value as executor default (unspecified).

The native `context_bytes`, `request_bytes`, `helper_value_bytes` and `response_wire_bytes` seed values are 4294967295, the existing helper framing ceiling. They bound distinct encoded byte paths, not model tokens. Reading a declared frame length does not allocate its claimed size; fallible bounded growth follows actual input. A short or truncated large frame fails without allocating the declared maximum. Actual memory and deadline limits remain effective, and full-window workload qualification is not inferred from this configuration.

The current definition-update policy revision is `v2-definition-updates-maximum-context-2`, with the twelve fields below. The operational diagnostic definition revision is `limits-feedback-v3-maximum-context`; its complete native override carries the selected context and byte-carrier values. An existing selected agent head is advanced only through a validated `update_definition` operation with exact current head/global/policy comparisons. New defaults or a submission carrying another immutable revision do not by themselves advance an existing head. Already accepted tasks remain pinned.

### Local Controller Storage

Controller startup inspects the actual opened directory and existing database, journal and ownership files before creating the owner lock or opening SQLite. It joins the opened descriptor's Linux mount identity to the kernel mount table. Recognized local block-filesystem families are ext4, XFS and Btrfs; network, FUSE, overlay, memory-backed and unverified filesystems are refused by this build. The database and its journal/coordination files remain on the admitted directory mount. Symbolic or hard-link file aliases and changed associations are refused without adopting them.

Metadata-only descriptors avoid disturbing an existing controller's SQLite locks. This checks local filesystem semantics under the trusted host boundary; it does not establish physical device transport, power-loss behavior, capacity or hostile-administrator protection. Current actual qualification uses this host's ext4 storage. Recognition of another local family is not qualification of that deployment. No stored format or historical target identity changes.

## Immutable Definition Settings

A new submission carries one immutable Definition with its identity, revision, executor, inference settings and execution profile. The inference object contains model and reasoning_effort; the current selected values are gpt-6-astra and max. The execution_profile is CollaborationV1, with native web_search absent unless explicitly selected. These fields belong to Definition, including a configured coding child's own Definition. There is no task-level or child-level duplicate profile. Reusing a definition identity/revision with changed settings refuses. Worker-wide model arguments do not override accepted template settings.

The new development deployment starts with empty current-format state and explicit inference and collaboration settings. Parent admission validates a configured child's settings before starting the parent. Exact replay within the current format retains the original committed operation outcome; resetting prototype data does not permit rewriting an outcome or duplicating a session within a running deployment.

A native task can additionally carry repository_read with an explicit repository identity and exact start_commit. Its absence exposes no repository content. Coding tasks use their accepted Repository or acknowledged checkpoint; they reject a separate native read association. Read scope never comes from another task or an optional child's repository. This does not grant workspace editing, arbitrary host paths or repository acquisition.

## Supported Definition-Limit Application

The trusted-host operator API exposes `update_definition` with `operation_id` and the same `DefinitionUpdate` payload. The browser settings form uses this operation through the canonical controller layer. It applies the same current change policy, selected-definition/global/policy revision comparisons, complete configuration validation, atomic revision selection and durable original receipt. This existing operator boundary does not manufacture an executing task caller. Agent MCP `collab_definition_update` continues to require its existing bound caller. Both interfaces select settings for future submissions; neither changes already accepted task snapshots.

`collab_definition_update` is a closed collaboration mutation under the existing caller and operation receipt. Inputs are `agent_id`, `expected_revision`, `expected_global_revision`, `expected_policy_revision`, and a nonempty `changes` object. Each change is a positive integer for an explicitly allowed field. The field vocabulary is `native.context_bytes`, `native.request_bytes`, `native.helper_value_bytes`, `native.response_wire_bytes`, `native.output_bytes`, `native.result_bytes`, `native.max_output_tokens`, `coding.command_output_bytes`, `coding.summary_chars`, `coding.summary_bytes`, `coding.model_context_window`, and `collaboration.complete_result_bytes`. A field outside this vocabulary or outside the active policy refuses; duplicate fields and malformed values refuse. The policy's field list is explicit metadata, not a numeric limit. The existing maximum-default model-request allowance is unchanged.

Optional global `definition_updates` metadata carries an immutable policy revision and allowed field list. Absence disables new updates and preserves historical metadata decoding. The installed controller compares the request against its active metadata and policy, rather than substituting the caller's historical metadata as today's policy. An accepted caller retains its original response, deadline and transport bounds. The existing limits read exposes both current policy and the caller's accepted settings.

The controller reads the selected definition and composes its effective limits with current defaults. It applies only requested field replacements, preserves all non-limit definition fields and every unrequested effective value at the compared global revision; a touched override group is materialized from those current effective values, and validates the complete resulting configuration with existing group and transport consistency checks. It records neutral/narrowing/widening over known effective resource allowances. If a changed `coding.model_context_window` was absent, classification is `previous_unspecified`; no numeric prior window is invented. That classification does not assert that other changed fields did not widen. The original definition and exact requested changes remain available for inspection. The configured allowed field class admits these changes without model approval or a new per-change human queue; it cannot edit the policy itself. A fresh controller-issued immutable revision, selected agent head and original success receipt commit together. A failure leaves the definition and head unchanged, with a durable refusal receipt where the canonical handler retains refusals. A replay returns that original result after cancellation or restart; changed input under its operation identity conflicts.

The result carries the previous and selected revisions, active global and policy revisions, changed fields, classification and `effective_for: future_submissions`. Reads of the selected agent expose the applied definition immediately after commit. Creating a new task from that selected definition resolves and retains its new values. Explicit task submissions remain allowed to use older immutable definitions but never advance or revert an existing selected head. Initial agent creation still establishes its first head. Existing sessions, accepted task limits and configured children remain pinned. Rollback is a new validated revision, not reuse of an old head revision.

A diagnosis task can inspect task history, attempts, effective limits and usage using the existing bounded catalogue and evaluate later tasks carrying the new definition revision. Evaluation links the exact change receipt; failed, uncertain, absent or truncated evidence is not success. No automatic retry, global hot reload, model/executor selection, host control installation, arbitrary definition body, permission engine or protected release action is part of this tool.

## Agent And Session Identity

The stable Definition.id identifies the agent (the reusable template); Definition.revision identifies an immutable configuration version. Session identity identifies one instantiation of that agent and is distinct from task/work identity and attempt identity. New instantiations get new sessions, while exact submission replay and recovery retain the existing association. Tasks and current attempts carry their session association to the worker and shared tools. Memory remains keyed by agent identity and key, shared across that agent's sessions with expected-revision checks. A session's pinned definition revision does not follow the latest agent-list selection silently. No separate per-instance durable-agent namespace is selected.

## Charter Source, Turn Binding And Reply Audit

A reusable charter is part of definition configuration, separate from TaskInput.instruction. The common contract carries a reference to the complete authoritative source and exact clause identities (source file, stable section, exact normative sentence). Reuse an immutable definition revision or existing document-version reference where it resolves that complete source. An authored clause alias resolves to this exact tuple; a rendered prompt, compacted summary, latest-head pointer or an unbound URL is not source authority. Resolution obeys existing access and retained-data rules and does not fetch or grant new access implicitly.

The initial source binding is retained in the accepted definition. An explicitly accepted later charter configuration change uses canonical operation identity, expected current charter binding and an immutable successor source. Root freezes the closed update/read shapes and existing caller route before implementation; the twelve-field definition-limit mutation remains limit-only and future-only. The session retains its pending charter binding separately from its effective binding and from accepted TaskInput. Just before building a turn request, after prior tool results commit, it atomically records the effective revision for that turn. A lost acknowledgment is reconciled under the original operation identity. Loading an active session checks pending adoption; an idle session is not woken solely to adopt it. No accepted model/executor/tools/budget/limit field changes through this path.

Native request construction supplies the effective charter and task instruction as distinct inputs. A changed native charter is delivered as a mid-conversation instruction and schedules one debounced low-priority compaction; a newer change joins an already due compaction and the summary is produced under that newer charter. Scheduling, effective source and compaction completion remain distinct recoverable facts. Compaction follows the selected native executor/provider path and existing finite deadline/accounting and context rules; audit checking alone does not schedule it. Supplied-executor charter changes use the pinned adapter's supported safe step event/input boundary, with model and tool calls quiescent. This adds no Borg compactor inside Codex and makes no claim about an unobserved internal cache or history rewrite.

Each turn reply carries a bounded structured metadata record identifying the turn occurrence, effective authoritative revision and governing clause references. Preserve the original received references alongside the deterministic check result, including unknown/malformed aliases, wrong revision, missing metadata, source-unavailable and exact-source mismatch observations. A check compares actual references to the turn's effective source; it neither replaces them with guessed clauses nor judges whether the behavior followed those clauses. An invalid check result is audit information, not an instruction to retry, reset, block work, compact or ask a model judge. Existing independent output-schema, currentness, deadline and side-effect rules still apply.

The durable reply record stores this metadata and the relevant original request/reply association. Any task result, history item or audit projection that cites the reply retains its association to that metadata, with bounded pagination/readback through existing controller records. A transport lookup receipt is not substituted for the original turn/reply identity. Failed commit, duplicate observation, restart and lost acknowledgment recover one original record without fabricating a provider result or repeating an unknown request. This requires a durable per-reply projection; current task summaries and final result records alone are insufficient. It does not require a full provider-neutral transcript service.

The shared section intentionally leaves streaming boundaries, empty applicability and charter-specific retention unspecified. The shared glossary defines a turn as one model request and its reply together with that reply's tool calls; an outer Codex turn or final task result does not redefine it. Before the concrete executor contract is frozen, root records the actual native response and supplied-executor signals that cover every such turn reply; how partial/failed streaming observations are associated; how an explicitly empty applicability list is represented without being labeled semantic compliance; and how source availability is retained for the chosen existing record policy. These are remaining representation decisions, not permission to omit metadata from supported replies. No time-to-live, semantic judge, blanket empty-list rejection or invented inner-turn visibility is selected here. The pinned Codex public notification union exposes completed items and outer turns, not a proven boundary for every upstream model reply. Internal raw-response type names do not create a supported subscription. That is a concrete qualification gap, not a narrower obligation; native work can proceed independently while the supplied-executor seam is resolved. Existing retained records are not pruned by this increment.

New fields and records require a deliberate wire/database/worker compatibility disposition and real old/new-reader cases. Missing historical charter metadata remains absent; an unsupported reader fails without rewriting accepted inputs, receipts or unresolved journals. Do not invent a release version or migrate stores in this proposal. The selected model, effort, dependencies, credentials, host access and protected release authority remain unchanged.

### Durable Mutation Replay

The wire separates transport correlation, mutation identity and external-effect identity. RegisterWorker and AwaitCommands carry an explicit operation ID. SettleOperation carries a separate settlement ID for its mutation receipt while preserving the original external operation ID in checkpoints and reconciliation. GetOperation resolves the exact recorded mutation by its mutation ID; looking up the external operation ID continues to return the external-effect record. Distinct settlement observations retain their own original outcomes after later observations, and conflicting input under a mutation ID never replaces a receipt. An equivalent final observation under a new settlement ID cannot rewrite the settled effect.

AwaitCommands arms change notification before inspection. With no change and no commands it remains pending under the same mutation ID, without filling the receipt store. Once an acknowledgment, admission or other state change commits, its response is recorded and returned even when the command list is empty. Replaying that receipt returns its original snapshot. A new request is created only after the prior response is durably consumed; a completion racing the HTTP wait does not discard its pending identity or acknowledgments.

Attempt admission reserves bounded control capacity for a run acknowledgment, the first recorded stop delivery and a stop acknowledgment. Only actual transitions can consume these credits; duplicate reads or acknowledgments cannot spend them. The delivery marker covers only commands included in the recorded response. A new attempt commits only when its run command is included in that exact response; existing commands and both page and byte bounds are accounted for before admission. At ordinary receipt exhaustion, command handling admits no new runs or deferred-state work and uses its reserved capacity only for cleanup. Prepared external operations also reserve one final-settlement receipt; unbounded uncertainty observations cannot consume that credit. Committed cleanup receipts and all outstanding reservations remain within the existing configured cleanup-receipt bound.

Workers persist exact registration, command-exchange and settlement inputs before sending, and persist an observed committed response before acting on its commands. Request, response-recorded and consumed phases prevent transport loss, cancellation or restart from changing the identity. A received launch is distinct from effects that may have begun. The worker records the latter state before workspace, process or provider work. A historical launch requires acknowledged start reporting and a fresh check of the current task, attempt, generation, worker incarnation, deadline and immutable input association before new effects. Neither cached acceptance nor a missing local file establishes current authority or proves that prior execution stopped.

Replacement registration accounts for an old pending exchange without treating absence of its receipt as a fence. If old admission commits first, its original command and any prior execution are reconciled before another logical registration request. If replacement registration commits first, the older incarnation cannot admit new work. An intact journal, exclusive local owner and actual process reconciliation are all needed to distinguish a received but unexecuted command from an attempt whose effects may have begun. Existing uncertainty and stop evidence remain separate.

Operator task controls retain their committed-revision comparison. Every ownership-generation transition increments that revision in the same immediate transaction, so a stale operator snapshot cannot pass after ownership changes. Revision and generation are different identities; the revision check validates the ownership state represented by that snapshot. Attempt-owned writes still compare their explicit task/attempt/generation tuple. Exact receipt replay and terminal cancellation no-ops do not perform a new task mutation.

HTTP route spelling and internal function names can follow these operations directly. There is no periodic database scan for ordinary work discovery, separate message broker, transaction across external I/O, custom signature service or generic RPC framework in this proposal.

Startup prerequisites remain immutable. Delegation creates a separate parent-child wait, not a new prerequisite on the parent and not an edge requiring the child to wait for its parent. Check the combined task-prerequisite and parent-child wait graph at delegation, including a child dependency that reaches the waiting parent through another task; reject cycles and delegation exceeding the configured maximum depth before creating the child. The parent releases its execution slot after its current execution has quiesced. Committing the child's terminal outcome settles the wait and makes its recorded outcome available to the parent's continuation; it does not automatically declare the parent successful. Repeated completion cannot resume the parent twice. Child deadlines and aggregate consumption remain within the parent's bounds. Delegation neither provisions credentials nor changes configured host, repository or provider access. Parent cancellation is propagated to outstanding delegated work through durable cancellation commands; unknown child effects remain unresolved rather than permitting a replacement execution.

Cancellation of a live parent follows the retained delegation lineage through terminal intermediate children; clearing the parent's current wait does not discard outstanding descendants. Existing terminal outcomes stay unchanged, and cancellation intent is not proof of termination. A cancellation request for an already-terminal root retains the existing terminal-result behavior. Queued-task views compute current admission reasons from the same eligibility checks as scheduling, including compatible registered-worker capacity. A visible eligible snapshot is neither a slot reservation nor proof that a worker is alive.

## Worker Commands And Reports

The command variants are RunAttempt and StopAttempt. A run carries the immutable task input, generation, worker incarnation, repository/start or committed checkpoint, executor profile, deadline, limits and any retained child outcome for a parent continuation. The controller keeps that child task/status/result association after settling the wait, including across restart; an instruction string does not substitute for it. A duplicate run for the same incarnation returns its existing status. A restarted worker refuses commands for an earlier incarnation.

Reports distinguish Started, Progress, ExecutorOutcome, ProcessTreeStopped, ExecutionUncertain, cumulative Usage and ResultCandidate. Usage counts known requests/tokens only; uncertainty is not erased by local process termination. A pre-request budget reservation requires an accepted controller response before the provider request; a pending outbox record alone is not admission. Only the controller accepts a final task result. A failed candidate with no executor outcome can settle platform acceptance only for the current verified-stopped attempt with no execution uncertainty or pending effect; the absent executor outcome remains absent. A successful candidate still requires an observed successful executor outcome. Progress events can be batched within output bounds without inventing durable records for unobserved inner model/tool attempts.

Native provider disposition is separate from local result validation and process cleanup. A request not started, an unknown remote outcome, and a fully observed terminal provider response are distinct typed observations. Receiving HTTP headers does not establish completion. Transport loss, partial or ambiguous response data retain uncertainty; a complete selected response can remain known even when its output later fails local schema validation. A complete bounded selected-provider rejection is recorded separately from an unknown effect. The retry successor recognizes an exact rate-limit rejection without treating status alone as proof; failed/incomplete envelopes, unsupported errors and ambiguous transport remain unknown. The existing uncertainty report prevents repetition of that effect until the remote outcome is reconciled; local process termination does not settle it. Retained older observations keep their original classification and are not rewritten.

A refused report is reconciled against its original operation identity before deciding whether it can be resent. An uncommitted infrastructure failure can retain the exact report for retry. A committed refusal remains immutable. Only a committed result refusal from the controller's identified validation-capacity, helper-failure or unverified-helper-cleanup paths is eligible for ReconcileResult; schema rejection, stale ownership, deadline expiry and ordinary input/result bounds do not qualify. The operation accepts no new output, validation assertion or authority field. A worker durably retains the original report, observed refusal and one reconciliation identity before sending the reconciliation, and resolves pending acceptance before registering a replacement incarnation. Neither a pending nor a refused acceptance is replaced by a fresh model request.

When ordinary receipt capacity is exhausted, the worker retains exact pending start, progress and usage records while allowing verified cleanup to proceed. Pending uncertainty is delivered before stop or terminal reports for the same attempt; unavailable critical state and pending result acceptance remain recovery barriers. Deferring an informational record does not authorize execution: initial start and pre-provider budget reservation still need accepted controller responses, and a received-only launch is not described as an executor outcome. No pending body is changed or discarded to obtain cleanup capacity.

Every coding workspace can run repository builds/tests directly. The worker enforces ordinary task and host-resource bounds; no separate build permit pool or four-build limit exists. Compiler parallelism is deployment configuration, not another coordination service. Eight active coding workspaces are measured while representative builds and native work occur; eight empty directories are not acceptance evidence.

The selected host-resource boundary is one cgroup v2 per worker and its execution descendants, set by ordinary startup configuration before child execution. Limits are shared, with headroom for builds and control/cleanup paths; no per-task reservation, dynamic rebalance or resource manager is introduced. Membership and configured-limit exhaustion/recovery are qualified against actual host controls. Disk capacity and durable-journal headroom remain separate filesystem work. This introduces no new task wire fields or stored-state representation.

### Worker Resource Profile

The worker's operator-only startup configuration accepts an optional `--resource-profile PATH`. It is separate from task/model input and carries a bounded JSON object with exactly these fields:

| Field | Meaning |
|---|---|
| `cgroup_path` | Absolute filesystem path to the configured worker cgroup directory. |
| `cpu_quota_us` | Expected positive finite CPU bandwidth quota per configured period. |
| `cpu_period_us` | Expected positive CPU bandwidth period. |
| `memory_max_bytes` | Expected positive finite memory ceiling. |
| `swap_max_bytes` | Expected finite swap ceiling; zero is valid. |
| `pids_max` | Expected positive finite process/thread ceiling. |

No numeric defaults or unlimited-value sentinel are introduced. The loaded profile stays fixed for the worker process; it is not hot-reloaded. Verification associates the opened directory with its actual cgroup2 mount and the worker's unified membership, without assuming a fixed mount location or namespace root. It accepts the normal domain form and exact configured leaf controls. Ancestor controls can further restrict available capacity; matching leaf values is not a throughput or headroom proof.

The operator establishes the group through ordinary host startup before worker execution. The worker reads and verifies controls; it does not create groups, move processes, change limits, install a service or provision privileges. When no profile is configured, the existing development path remains available without a hard-resource qualification claim. An explicitly configured but invalid, unavailable or mismatched profile has no unbounded fallback.

Startup first obtains the existing exclusive worker ownership and reconciles owned prior processes. Resource refusal preserves journals and permits bounded retained-result/report cleanup, but does not resend a work-producing command wait or create a saved-delegation child. Validated controls gate capacity registration, subsequent new work and the final launch boundary after asynchronous currentness checks. Existing cancellation, shutdown and reaping remain responsible for termination evidence. These checks do not introduce a polling resource monitor or per-task reservation mechanism.

## Recovery And Race Cases

| Case | Expected result |
|---|---|
| Lost SubmitTask acknowledgment | Lookup/retry of the same operation returns one task. Different input under its ID refuses. |
| Controller restart while worker runs | Reconcile the existing attempt; do not create a competing one. |
| Duplicate RunAttempt | Existing execution/outcome returned; no second app-server turn. |
| Worker restart with surviving children | New incarnation remains unavailable until prior processes are accounted for/stopped. |
| Tunnel disconnect or interrupt acknowledgment | Unknown connectivity or requested stop; neither proves stopped execution. |
| Cancellation races with completion | First committed transition controls acceptance; cancelled-first cannot later accept success. |
| Stale result or memory update | Historical observation at most; no mutation of current accepted state. |
| Git push succeeds before task checkpoint commits | Inspect the original attempt-specific remote reference and exact commit; settle that publication, then commit its checkpoint. |
| Lost PR/merge response | Observe the original intended operation; unknown cannot be blindly retried. |
| Parent waits for delegated work | Child and separate wait commit once; immutable prerequisites remain unchanged; release the parent's quiescent execution slot; child outcome settles the wait once without automatically accepting the parent. |
| Failed prerequisite | Dependent task remains visibly blocked, never silently treats failure as success. |
| Reconnect/resume | Original deadline and accepted request accounting survive; no reset of limits, debits or reservations through transport churn. |
| Executor exits successfully but checks fail | Task is not accepted as successful. |
| Merge succeeds | No automatic rollout; final artifact/target authorization remains required. |

External-operation identities use the receiving interface's actual deduplication or observable outcome where available. A generic exactly-once guarantee for arbitrary shell side effects is not offered. If an operation cannot be reconciled safely, the task reports the concrete unresolved outcome instead of inventing success or retry safety.

## Frozen Request And Result Shape

The private application wire revision is 4; it is independent of the implementation identifier v2. Each request has `protocol_revision`, `operation`, `request_id` and typed `input`. Mutations additionally carry the durable mutation identity described above: an operation ID, report ID or settlement ID according to the operation. `request_id` matches one transport response and is not an effect-deduplication key. Identities are opaque nonempty strings within configured byte bounds. Task revisions/generations and committed order positions are checked nonnegative integers; their storage width does not carry business meaning. Reject an unsupported wire revision or unknown operation before mutation.

A response echoes `request_id` and has one of `ok`, `refused`, `pending` or `uncertain`. A committed mutation outcome carries its operation ID and committed task/controller revision. Refusals distinguish invalid input, unsupported version/operation, conflicting operation identity, stale revision/generation, invalid task transition and bounded-capacity refusal. Diagnostic messages are bounded and contain no credentials. Transport failure does not synthesize a successful operation or erase an existing durable intent. Clients use the original operation ID for lookup/retry.

### Committed Mutation Context

Replies separate the immutable mutation receipt from the revision observed by the current request. Without a mutation receipt, `commit` is null. Otherwise it contains the original `operation_id` and positive `controller_revision`. The `observed_controller_revision` field identifies the database snapshot used for the reply; it can be null when no database observation completed. Task revisions remain separate fields on task records. These counters order one intact controller database lifetime, not unrelated or replacement databases.

The controller records a checked revision with every new mutation receipt in the same transaction as its outcome and effects. Recorded refusals and accepted no-op outcomes also have receipts. A deadline transaction that changes state advances the controller revision. Read-only calls, empty pending waits and exact receipt replays do not advance it. A rollback or unknown commit outcome returns no invented commit stamp. Exhausting the supported revision range refuses a new write rather than wrapping or resetting it.

Exact mutation replay carries the original commit stamp, even when the current observed revision is later. An application-mutation lookup carries that same stamp alongside its original intended request and outcome. Looking up an external-effect identity instead returns its current effect state with no original-mutation stamp; the observation revision does not pretend that a later settlement was the original preparation outcome. Reusing an operation identity with different input returns an uncommitted conflict decision and never borrows the original receipt's stamp.

Before accepting a new receipt, both its direct replay and its application-mutation lookup representation fit the existing response bound, including the original request and the maximum permitted correlation and revision framing. Command selection accounts for that request-specific overhead before admitting an attempt; omitted work remains queued. A receipt is not accepted merely because its first response used a shorter transport identity.

Consumers check the operation identity, positive commit revision and its relationship to the observed revision before treating a successful mutation as committed. Pending responses and uncommitted refusals do not settle an unknown original operation. In particular, a delegation capacity refusal without a receipt remains pending under the original identity; it does not prove that no child exists. Worker journals retain original committed context with recorded outcomes. A local no-send disposition remains explicitly local and carries no fabricated controller stamp. Historical context is neither current ownership nor permission to start an effect; the existing fresh authority and cleanup checks still apply.

Task input includes the immutable instruction/definition revision, initially requested agent identity, executor kind, acceptance command descriptors or native output schema, finite bounds, existing prerequisite IDs, and repository plus starting commit for coding work. The agent is the stable identity of the accepted definition. The session association is server-owned and distinct from task and attempt identities; assignment cannot silently select a different memory namespace or change an accepted definition. Server-owned assignment/attempt/status/result fields cannot be supplied as accepted facts. Worker reports carry the existing worker/incarnation/task/attempt/generation tuple, a report identity, a closed observation kind and bounded payload. Native and coding result candidates enter the same controller acceptance transition; neither producer writes the database directly.

The first network adapter uses one private HTTP JSON operation endpoint, `POST /api/operations`, and a health endpoint; the browser exposes task list/detail/create/action routes through the product module. Browser form handlers use the same typed application operations directly in the controller process rather than opening the database themselves. The controller exports one operation handler, the worker/native adapters consume one controller-client interface, and the product consumes that same handler. Interfaces expose owned request/result records and ordinary bounded async calls; avoid public lifetime-dependent projection/factory contracts. Exact function names stay with the integrator.

## Discriminating Interface Cases

- A queued assignment succeeds once; retry returns the same outcome; stale or already-active assignment cannot create a competing owner.
- Two sessions of one agent can execute concurrently and share its memory. A session cannot admit a second live execution; a quiescent parent's delegated wait permits child work without overlapping the parent session's execution or losing its recorded continuation. Distinct agents retain distinct memories; concurrent writes use expected memory revisions.
- Oldest-eligible admission follows durable submission order, skips a blocked dependency or exhausted executor capacity, and never consumes a coding slot for a native-only request.
- A browser refresh/reconnect displays committed assignment/status/result, preserves an uncertain operation indicator, and cannot manufacture success from a stale page. Repeating a form submission reuses its operation ID.
- Hostile text in task instructions/output renders as text, not executable browser markup. State-changing actions use non-GET requests with same-origin checks; possession of an arbitrary identity field is not authentication. These are ordinary private-UI correctness checks, not a new grant engine.
- A pushed WIP commit is fetchable on another worker while remaining an unfinished task. Wrong commit, changed content under the publication identity, missing acknowledgment and stale-attempt publication cannot select a false checkpoint.
- Unsupported/corrupt task-state schema is refused without rewriting original bytes. A planned migration has an explicit old/new version and rollback/recovery disposition before application; it does not promise indefinite historical readability.
